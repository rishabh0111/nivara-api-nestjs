# CORS decided per request, split by credential model

This API serves two kinds of browser caller, and no single CORS configuration satisfies both. The portal and the staff dashboard hold an httpOnly refresh cookie, so their requests are credentialed — and a credentialed request may not be answered with a wildcard origin, because the browser requires an exact echo. Their origins therefore have to be known in advance, which they are: they are deployments of the front end, listed in `WEB_ORIGINS`. The widget is the opposite. It runs on tenants' own sites, so its origins cannot be enumerated in this repository at all, and it presents a bearer token rather than a cookie, so it needs nothing credentialed.

So **CORS is a per-request delegate**: every origin is echoed, and `credentials` is granted only to an origin on the first-party list. The alternative that looks simpler — `origin: true, credentials: true` — would make the refresh cookie reachable from any page on the internet, which matters more here than it usually would, because the cookies are `SameSite=None` by necessity ([the cross-origin front end](../../README.md#authentication) is on another registrable domain). Permissive credentialed CORS and a cross-site-sendable cookie are CSRF with the door held open.

**The widget's origin allowlist is deliberately not enforced here, and could not be.** It is per tenant, stored on the tenant row, and the request names its tenant in the body — but a preflight is an `OPTIONS` with no body, so at CORS time there is no `tenantId` and therefore no allowlist to consult. Enforcing it here would mean enforcing it one request too early on information the request has not yet supplied. It is checked instead inside the bootstrap endpoint, by `originIsAllowed`, where the tenant is known. That check is the actual gate; this policy is not a security boundary and is not written as one. Reflecting an unknown origin is safe precisely because reflecting it grants nothing that the endpoint behind it does not separately verify.

Two smaller consequences. Rate-limit and idempotency response headers are named in `exposedHeaders`, because a browser hides every response header a server does not explicitly expose — an unreadable `Retry-After` is a 429 a client can only answer by guessing, which turns a backoff into a retry storm. And an empty `WEB_ORIGINS` grants credentials to nobody rather than to everybody: an instance with no browser front end deployed against it is an ordinary configuration, not a reason to open up.

The cost accepted is that origins are configuration, so a front-end deployment at a new URL — a preview deploy, a renamed project — cannot reach the API until it is named. A wildcard over the hosting platform's domain would fix that and is refused on the same grounds as everything above: it would grant credentialed access to every site any customer of that platform hosts.
